# 12 — Observability

**Spec refs:** §46, §53

---

## 1. Tracing

`tracing` + `tracing-subscriber`, JSON-formatted in preview/production, pretty locally.

Every span carries the correlation fields §46 asks for:

| Field | Where it originates |
|---|---|
| `request_id` | generated by middleware, returned as `X-Request-Id` |
| `job_id` | the job row |
| `crawl_id` | one deduped fetch; shared by every `backlink_checks` row it produced |
| `organization_id` | from `OrgScope`, on tenant-scoped work only |
| `worker_id` | `locked_by` |
| `duration_ms` | closed by the span |
| `result` | a small enum, not free text — so it aggregates |

`crawl_id` is the important one: it ties a single HTTP request to the N backlinks it resolved, which
is how "why did this backlink change state" is answered in one query, and how the dedup ratio is
measured.

**Never logged:** passwords, session tokens, CSRF tokens, Stripe keys, DSN credentials, email
bodies, raw response bodies (§46, [S10](11-security-risks.md#s10--secret-leakage-in-logs--medium)).

## 2. Metrics

Prometheus text at `/metrics` on the API and the worker, behind a shared secret.

### API
- `http_request_duration_seconds{route,method,status}` — histogram
- `http_requests_total{route,method,status}`
- `db_query_duration_seconds{query}` — Neon latency, which we do not control and must watch
- `db_pool_connections{state}` — idle / active / waiting
- `db_pool_acquire_timeouts_total` — the leading indicator of pool starvation

### Worker & queue
- `queue_depth{job_type,status}`
- `job_age_seconds{job_type}` — **the health metric**: oldest pending job. Depth can look fine while
  one job type starves.
- `job_duration_seconds{job_type,result}`
- `job_attempts_total{job_type,result}`
- `jobs_dead_total{job_type}` — alerts on any increase
- `jobs_reaped_total` — non-zero means workers are dying

### Crawler (§53)
- `crawl_duration_seconds{outcome}`
- `crawl_requests_total{outcome}` — ok / http_error / timeout / blocked / oversized
- `crawl_bytes_total`
- `crawl_retries_total`
- **`crawl_dedup_ratio`** — `backlinks_checked / http_requests`
- `domain_semaphore_wait_seconds`
- `robots_blocked_total`

### Business (§53 crawler economics)
- `backlinks_monitored{organization_id}`
- `unique_source_urls`
- `checks_completed_total`
- `requests_per_1000_backlinks` — derived; the unit-economics number
- `state_transitions_total{from,to}` — a spike in `live→lost` is either a real event or a bug in the
  state machine, and either way we want to know within minutes

## 3. Alerts

| Condition | Severity |
|---|---|
| `job_age_seconds{job_type="check_source_page"} > 3600` | page |
| `jobs_dead_total` increasing | page |
| `db_pool_acquire_timeouts_total` increasing | page |
| `crawl_requests_total{outcome="blocked"}` ratio > 10% | warn — likely a guard bug or an IP block |
| `crawl_dedup_ratio` < 1.5 | warn — the cost model is degrading |
| `state_transitions_total{to="lost"}` > 5× 7-day baseline | warn — suspect a bug before believing it |
| API 5xx rate > 1% over 5 min | page |
| `jobs_reaped_total` increasing | warn — workers are being killed |

The `live→lost` spike alert exists because the expensive failure here is **not** downtime — it is
confidently telling hundreds of customers their links are gone when they are not. §24's confirmation
logic prevents it per-link; this alert catches a systemic version.

## 4. Crawler economics (§53)

Recorded per check, rolled up daily into `usage_records`:

| Metric | Use |
|---|---|
| unique source URLs vs backlinks monitored | the dedup multiplier |
| HTTP requests per 1000 monitored backlinks | the cost driver |
| bytes downloaded | egress cost |
| average response time | worker sizing |
| retry rate | publisher reliability and our own politeness |

Target: **infrastructure cost per 1000 monitored backlinks**, per §53 the core SaaS metric. It is
computed from these inputs plus the worker/Neon bill, reported monthly, and compared against plan
pricing (§39) — a plan whose cost per backlink exceeds its price per backlink is a pricing bug that
should surface in a dashboard rather than in an invoice six months later.
